# Heron 内容生产线架构设计

**文档版本：** v1.0  
**状态：** 架构提案  
**适用项目：** Heron 后端 / Heron UI  
**核心目标：** 建立一个能够自动发现有价值的信息、理解内容价值、完成故事策划、生产高质量短视频，并通过真实发布数据持续优化的智能内容生产系统。

---

# 1. 项目定位与设计目标

## 1.1 产品定位

Heron 不应该只是一个 AI 视频生成工具。

它应该是一个：

**以内容价值为中心，以 AI 编辑策划为核心，以自动化视频制作为手段，以真实用户反馈为优化依据的智能短视频内容生产平台。**

系统的核心任务不是尽可能多地生成视频，而是持续回答以下问题：

1. 今天有什么值得观众看的内容？
2. 为什么观众会对这个内容感兴趣？
3. 应该从什么角度讲，才能让内容有吸引力？
4. 如何把内容组织成一个完整、易懂、有节奏的故事？
5. 应该使用什么画面、图表、动效和声音来表达？
6. 成片是否真正值得发布？
7. 发布之后，观众是否愿意继续看、点赞、评论和分享？
8. 如何利用真实反馈改进下一条视频？

最终形成：

**内容发现 → 价值判断 → 编辑策划 → 事实研究 → 故事设计 → 分镜规划 → 视频制作 → 质量审核 → 发布 → 表现分析 → 策略优化**

的完整闭环。

## 1.2 核心业务目标

- 持续生产有价值、有吸引力的短视频。
- 支持多个内容方向，而不是围绕一种视频形式发展。
- 数据看板线作为当前主要生产方向。
- 热点新闻线负责捕捉短期热点机会。
- 新增趋势洞察线和知识解释线，形成更加完整的内容体系。
- 统一基础设施，避免每条内容线重复建设生产流程。
- 支持全自动生产，也支持人工介入和人工发布。
- 支持 NO_PUBLISH，不允许为了产量而降低内容质量。
- 基于实际播放、完播、互动和关注转化持续优化。

## 1.3 非目标

当前阶段不以以下目标为核心：

- 不追求无限增加视频生产线。
- 不为每条内容线开发一套独立的视频渲染引擎。
- 不单纯追求每天生成多少条视频。
- 不把新闻数量、数据数量当作内容价值。
- 不通过模型凭空编造数据、因果关系和预测。
- 不把一次成功的视频当成可重复的爆款规律。
- 不引入没有实际收益的复杂 Agent、微服务和中间件。

# 2. 内容生产体系：四条核心生产线

Heron 第一阶段采用四条内容生产线。

| 内容线 | 内部标识建议 | 内容驱动方式 | 优先级 |
|---|---|---|---|
| 热点新闻线 | NEWS_EXPLAINER | 事件驱动 | P1 |
| 数据看板线 | DATA_BOARD | 数据驱动 | P0 |
| 趋势洞察线 | TREND_INSIGHT | 趋势与多源数据驱动 | P1 |
| 知识解释线 | KNOWLEDGE_EXPLAINER | 知识与问题驱动 | P2 |

其中 DATA_BOARD 和 NEWS_EXPLAINER 是现有业务的延续。

新增的 TREND_INSIGHT 和 KNOWLEDGE_EXPLAINER 应当逐步建设，不要求第一阶段全部上线。

## 2.1 热点新闻线（NEWS_EXPLAINER）

### 定位

围绕正在发生的新闻事件，快速判断事件价值，向观众解释事件本身、重要事实以及已经得到证据支持的影响。

核心不是复述新闻，而是回答：

**发生了什么？为什么值得关注？它会带来什么已经有依据的影响？**

### 主要内容栏目

- AI 行业热点
- 科技公司重大事件
- 商业和财经热点
- 社会热点
- 全球重要事件
- 产品发布与重大技术突破

### 典型选题

- 某家公司宣布重大产品发布。
- 某项新技术出现重大突破。
- 某个行业发生重要政策变化。
- 某家企业发布超预期财报。
- 某个事件引发广泛讨论。

### 典型叙事结构

1. 开头：用最重要的事实或冲突吸引注意力。
2. 背景：交代事件发生的背景。
3. 事实：解释核心事件和关键细节。
4. 影响：分析有证据支持的影响。
5. 结尾：总结事件价值或提出值得关注的问题。

### 关键质量要求

- 新闻时间必须明确。
- 重要事实必须有可靠来源。
- 区分事实、推断和观点。
- 多来源信息冲突时不能随意选择。
- 过期新闻不能伪装成突发新闻。
- 不制造标题党和虚假因果关系。
- 新闻价值不足时允许 NO_PUBLISH。

### 关键指标

- 新闻时效性。
- 来源可信度。
- 事件影响范围。
- 选题差异化。
- 事实核验通过率。
- 发布时效。
- 平均播放时长和互动率。

## 2.2 数据看板线（DATA_BOARD）

### 定位

这是 Heron 当前最重要的内容生产线。

通过真实数据、排行榜、对比、变化和可视化分析，持续输出观众容易理解、有明确价值的短视频。

核心回答：

**现在的数据是什么？发生了什么变化？谁领先？谁落后？**

数据看板不应该只是把一张报表转换成视频。

每条视频必须找到一个值得展示的数据主题。

### 主要内容栏目

| 栏目 | 主要表达 | 示例 |
|---|---|---|
| 排行榜 | 排名、TOP N | 全球 AI 模型排行榜 |
| 数据对比 | A 与 B 的差异 | 不同汽车品牌销量对比 |
| 增长变化 | 时间序列变化 | 本月 AI 产品增长情况 |
| 数据盘点 | 分类和总体情况 | 全球主要科技公司收入 |
| 异常发现 | 突然增长、下跌或反常数据 | 某款产品使用量突然增加 |
| 地域分布 | 地区和国家差异 | 全球 AI 算力分布 |
| 周期报告 | 日报、周报和月报 | 本周 AI 行业数据总结 |

### 典型叙事结构

1. 开头：最值得关注的数据结论或反差。
2. 展示：呈现核心数据和排名。
3. 对比：解释关键对象之间的差异。
4. 发现：突出最有价值的变化。
5. 结尾：总结观众应该记住的信息。

### 关键质量要求

- 每项关键数据都有来源。
- 保留统计时间和统计口径。
- 明确单位、币种和数据范围。
- 数据缺失不能自动补成真实数值。
- 排名和对比必须使用相同或可解释的统计口径。
- 样本量不足时不得夸大结论。
- 不允许从相关性直接推导因果关系。
- 图表必须准确表达真实数据。

### 关键指标

- 数据准确率。
- 数据源可信度。
- 数据新鲜度。
- 选题独特性。
- 图表可读性。
- 信息密度。
- 完播率。
- 分享率和收藏率。

## 2.3 趋势洞察线（TREND_INSIGHT）

### 定位

这是最值得 Heron 新增的内容生产线。

它与数据看板线有明显区别：

- DATA_BOARD：告诉观众发生了什么。
- TREND_INSIGHT：解释这些变化意味着什么。

它需要通过多时间段、多维度、多来源的数据分析，发现增长趋势、竞争格局变化、异常现象和有价值的行业变化。

### 主要内容栏目

| 栏目 | 主要内容 | 示例 |
|---|---|---|
| 行业趋势 | 行业整体变化 | AI 行业正在发生什么变化 |
| 公司洞察 | 企业经营与竞争 | 为什么某家公司增长更快 |
| 产品趋势 | 产品增长和竞争 | 哪些 AI 产品正在快速崛起 |
| 消费趋势 | 用户消费和偏好 | 年轻人的消费变化 |
| 技术趋势 | 技术发展方向 | AI Agent 技术的发展变化 |
| 社会趋势 | 社会、人口和就业变化 | 哪些行业的就业需求发生变化 |

### 典型叙事结构

1. 开头：提出一个值得思考的问题或反常识现象。
2. 现象：展示已经观察到的变化。
3. 证据：使用多个数据或案例支撑判断。
4. 解释：分析可能的原因，明确证据与推测的边界。
5. 洞察：说明趋势可能意味着什么。
6. 结尾：总结判断，提出仍需观察的问题。

### 示例

选题：为什么 AI Agent 最近越来越受关注？

不能只做一个 AI Agent 产品排行榜。

应该进一步研究：

- 过去一段时间产品数量如何变化？
- 用户关注度是否增长？
- 主要产品的能力和定位有何区别？
- 市场竞争格局是否发生改变？
- 哪些结论有真实数据支持？
- 哪些只是行业观点或预测？

最终产出一条有观点、有证据、有逻辑的趋势分析视频。

### 关键质量要求

- 尽可能使用多时间点数据。
- 多来源数据必须处理统计口径差异。
- 区分观察到的现象和可能的原因。
- 趋势结论需要证据支持。
- 不得把短期波动直接描述为长期趋势。
- 不得把模型推测写成确定事实。
- 关键观点必须能追溯到具体证据。

### 关键指标

- 趋势判断的证据充分度。
- 数据覆盖范围。
- 观点独特性。
- 信息增量。
- 论证完整性。
- 平均播放时长。
- 完播率。
- 评论讨论率和分享率。

## 2.4 知识解释线（KNOWLEDGE_EXPLAINER）

### 定位

面向普通观众，把复杂的技术、经济、商业和社会概念转化为简单易懂的视频内容。

核心回答：

**这是什么？为什么会这样？它是如何工作的？**

这条线的内容不一定依赖当天的热点，也不一定需要最新数据。

它可以形成可持续积累的长期内容资产。

### 主要内容栏目

| 栏目 | 主要内容 | 示例 |
|---|---|---|
| 概念科普 | 解释术语 | 什么是 Token |
| 原理拆解 | 解释运行机制 | AI Agent 如何工作 |
| 技术解释 | 技术知识 | GPU 为什么适合 AI 训练 |
| 商业知识 | 商业逻辑 | SaaS 为什么能持续收费 |
| 经济知识 | 经济规律 | 降息为什么会影响股市 |
| 案例教学 | 通过实际案例理解知识 | 一个 AI 产品是如何赚钱的 |
| 误区纠正 | 解释常见误解 | 模型参数越大就一定越好吗 |

### 典型叙事结构

1. 开头：提出观众可能遇到的问题。
2. 定义：用最简单的话解释概念。
3. 拆解：把复杂机制拆成几个容易理解的部分。
4. 例子：用生活场景或真实案例解释。
5. 结论：让观众真正记住这个知识点。

### 示例

选题：什么是 Token，为什么 AI 会按照 Token 收费？

叙事过程：

- 先展示用户输入一段文字的场景。
- 解释模型如何把文字拆成 Token。
- 展示 Token 和字数并不完全等价。
- 解释输入和输出 Token 的区别。
- 用一个费用例子说明 Token 计费。

### 关键质量要求

- 概念定义准确。
- 解释过程不能偷换概念。
- 例子需要合理。
- 尽可能避免过度专业化。
- 不能为了简化而造成事实错误。
- 知识来源可以追溯。
- 内容应当有清晰的学习收益。

### 关键指标

- 概念解释准确度。
- 内容易懂程度。
- 记忆点。
- 平均播放时长。
- 完播率。
- 收藏率。
- 评论中的知识理解反馈。

# 3. 内容线与栏目体系

必须明确区分以下几个概念：

| 概念 | 定义 | 示例 |
|---|---|---|
| 内容生产线 | 定义内容生产策略 | DATA_BOARD |
| 内容栏目 | 某条线下持续生产的主题分类 | 排行榜 |
| 选题 | 一期具体内容 | 全球 AI 模型排行榜 |
| 内容方案 | 一期视频准备表达的观点和叙事 | 谁领先、差距有多大 |
| 视频风格 | 视觉表达方式 | 新闻播报、数据调查 |
| 视频模板 | 可以渲染的具体实现 | news-data-broadcast-9x16 |
| 视频成片 | 最终生产结果 | episode.mp4 |

建议采用以下层级：

```text
Heron
 └── Content Line
      └── Content Series
           └── Topic / Candidate
                └── Editorial Brief
                     └── Story Plan
                          └── Storyboard
                               └── Video Episode
```

**不要让每个栏目都拥有独立的渲染系统。**

栏目主要决定内容主题、选题规则和表达方式，而不是复制一套生产管线。

## 3.1 栏目与内容线的对应关系

```text
热点新闻线
 ├── AI 行业热点
 ├── 科技公司动态
 ├── 商业财经热点
 └── 社会热点

数据看板线
 ├── 排行榜
 ├── 数据对比
 ├── 增长变化
 ├── 异常发现
 ├── 地域分布
 └── 周期报告

趋势洞察线
 ├── 行业趋势
 ├── 公司洞察
 ├── 产品趋势
 ├── 消费趋势
 └── 技术趋势

知识解释线
 ├── 概念科普
 ├── 原理拆解
 ├── 技术解释
 ├── 商业知识
 └── 案例教学
```

案例拆解不单独建设第五条生产线。

它可以作为趋势洞察线和知识解释线下的栏目，根据内容目标选择对应的编辑策略。

# 4. 总体系统架构

## 4.1 设计原则

Heron 采用：

**多内容线策略 + 统一编排引擎 + 统一视频制作引擎 + 统一发布反馈系统。**

内容线只负责内容策略差异，底层生产能力尽可能复用。

## 4.3 系统模块职责

### A. 内容发现模块

负责从不同来源发现可以生产的视频选题。

每条生产线可以拥有不同的发现策略，但统一输出候选选题。

输出：

- 候选标题。
- 内容线建议。
- 栏目建议。
- 内容来源。
- 发现时间。
- 原始信息。
- 数据或事件摘要。
- 初始价值评分。

### B. 编辑决策模块

这是整个系统最重要的业务决策模块。

负责：

- 判断候选内容是否值得生产。
- 决定应该走哪条生产线。
- 判断内容适合哪个栏目。
- 选择故事角度。
- 决定目标受众。
- 决定内容核心观点。
- 决定视频时长和表达方式。
- 必要时拒绝生产。

必须保留编辑决策的最终控制权。

不能因为某个 Agent 生成了脚本，就默认内容值得发布。

### C. 事实研究模块

统一管理不同类型内容的事实证据。

重点是建立 Evidence Pack：

```text
Evidence Pack
 ├── Evidence ID
 ├── Source Name
 ├── Source URL
 ├── Published At
 ├── Captured At
 ├── Fact Value
 ├── Unit
 ├── Scope
 ├── Time Range
 ├── Verification Status
 └── Confidence / Notes
```

其中：

- 新闻线重点关注来源可信度和事件时间。
- 数据线重点关注原始数据、口径、单位和快照。
- 趋势线重点关注跨时间和多源数据的一致性。
- 知识线重点关注概念、原理和权威资料。

所有重要结论都必须能追溯到对应证据。

### D. 内容创作模块

负责把编辑方案转换成可以生产的视频内容。

包括：

- 故事结构设计。
- 标题和开场设计。
- 旁白文案。
- 分镜设计。
- 画面内容规划。
- 字幕设计。
- 图表表达。
- 转场和动效意图。

模型可以负责创作，但必须通过结构化契约约束输出。

### E. 视频制作模块

所有生产线共用。

继续使用当前技术：

- HyperFrames。
- GSAP。
- HTML / CSS / SVG。
- Edge TTS 及后续可替换语音提供方。
- FFmpeg。
- FFprobe。
- MinIO。

当前阶段不增加第二套独立渲染框架。

### F. 质量审核模块

统一质量框架，根据不同内容线使用不同的审核规则。

### G. 发布与反馈模块

统一管理：

- 发布记录。
- 发布尝试。
- 发布状态核对。
- 播放数据。
- 互动数据。
- 内容效果分析。
- 策略反馈。

发布状态不明确时，不允许盲目重复发布。

# 5. 核心生产流程

所有生产线走同一个编排主流程，但策略、上下文和质量标准由具体内容线决定。

不能为了实现这套流程，直接推翻已有的任务状态、发布保护和异步任务机制。

## 5.2 关键设计要求

### 编辑方案必须冻结

当选题确定后，必须保存本次生产所使用的：

- 内容线。
- 栏目。
- 选题角度。
- 核心观点。
- 目标受众。
- 数据快照版本。
- 事实证据。
- 内容策略版本。

后续生产不得悄悄替换已经冻结的核心事实。

如果原始数据发生变化，应明确执行重新核验或重新策划，而不是静默使用新数据。

### 允许不同步骤独立重试

例如：

- TTS 失败，只重试语音生成。
- 某个素材失败，只重试该素材。
- 渲染失败，只重试渲染。
- 内容审核不通过，退回对应步骤。
- 发布结果未知，先人工核对，不直接重复发布。

不能为了一个步骤失败，重新执行整个生产链路。

### NO_PUBLISH 是正常结果

以下情况可以直接不生产：

- 热点没有足够价值。
- 数据缺乏可信来源。
- 选题没有明显的信息增量。
- 叙事无法成立。
- 视觉无法有效表达。
- 成片质量不足。
- 已有同类内容重复度过高。

# 6. 编辑策划与选题评分

## 6.1 统一选题评分体系

所有候选选题采用 0～100 分的评分体系。

但各条生产线拥有不同的评分权重。

评分只是辅助编辑决策，不能覆盖事实核验等硬性门禁。

### 热点新闻线

| 维度 | 初始权重 |
|---|---:|
| 时效性 | 25% |
| 事件影响力 | 20% |
| 信息可信度 | 25% |
| 选题差异化 | 15% |
| 观众相关性 | 15% |

### 数据看板线

| 维度 | 初始权重 |
|---|---:|
| 数据可信度 | 25% |
| 数据变化或反差 | 25% |
| 观众兴趣 | 20% |
| 选题独特性 | 20% |
| 视觉表达潜力 | 10% |

### 趋势洞察线

| 维度 | 初始权重 |
|---|---:|
| 趋势证据充分度 | 25% |
| 信息增量 | 20% |
| 观众相关性 | 20% |
| 分析深度 | 20% |
| 视觉表达潜力 | 15% |

### 知识解释线

| 维度 | 初始权重 |
|---|---:|
| 观众需求 | 25% |
| 知识价值 | 25% |
| 解释清晰度 | 20% |
| 内容差异化 | 15% |
| 视觉表达潜力 | 15% |

以上权重为第一阶段策略配置，应允许调整，并保留评分原因。

## 6.2 硬性门禁

以下情况不能通过简单加权评分绕过：

- 无法确认核心事实。
- 数据来源不明。
- 关键结论没有证据。
- 存在明显误导。
- 内容重复且没有新的信息价值。
- 涉及高风险内容但缺少必要审核。

## 6.3 编辑策划输出

每条选题至少需要形成：

```json
{
  "contentLine": "DATA_BOARD",
  "series": "RANKING",
  "targetAudience": "关注AI产品的普通用户",
  "editorialIntent": "展示当前AI模型竞争格局",
  "storyAngle": "排名变化比单纯排名更有看点",
  "coreThesis": "需要证据支持的核心结论",
  "audienceValue": "观众看完能够获得什么",
  "hookStrategy": "通过排名变化和差距建立悬念",
  "targetDurationSeconds": 45,
  "publishRecommendation": "PRODUCE",
  "reasons": []
}
```

实际字段名称需要适配当前 Java 对象和现有 JSON 命名规范，避免并行创建两套字段体系。

# 7. 故事结构与脚本契约

这是 Heron 下一阶段最重要的升级点。

当前脚本不能只停留在：

```text
标题 + 几段 lead/body + closing
```

因为这样的结构主要解决的是文案生成问题，不足以解决视频导演问题。

## 7.1 增加 Story Plan

正式写旁白之前，先生成结构化故事计划。

Story Plan 至少包括：

- 核心观点。
- 故事结构。
- 开场钩子。
- 各段叙事目的。
- 证据引用。
- 情绪和节奏。
- 预期视觉表达。
- 结尾信息。

## 7.2 统一脚本契约 v2

建议向以下结构演进：

```json
{
  "contractVersion": "2",
  "title": "视频标题",
  "hook": {
    "type": "contrast",
    "purpose": "吸引观众继续观看",
    "narration": "开场旁白"
  },
  "thesis": "核心观点",
  "audienceValue": "观众能够获得的价值",
  "scenes": [
    {
      "sceneId": "scene-01",
      "beat": "HOOK",
      "purpose": "建立兴趣",
      "narration": "旁白内容",
      "onScreenText": "画面文字",
      "evidenceRefs": [],
      "visualIntent": {
        "type": "HIGHLIGHT",
        "dataRefs": [],
        "emphasis": "重点突出",
        "transition": "REVEAL"
      },
      "durationHintSeconds": 5
    }
  ],
  "closing": {
    "narration": "结尾内容",
    "purpose": "强化记忆"
  }
}
```

这里的 `visualIntent` 是视觉表达意图，不是允许模型直接输出任意 HTML、CSS 或 JavaScript。

具体可用的视觉组件由 Java 契约和 HyperFrames 模板提供。

## 7.3 Story Beat 类型

建议建立有限的故事节点类型：

| 类型 | 用途 |
|---|---|
| HOOK | 开场吸引注意力 |
| CONTEXT | 交代背景 |
| QUESTION | 提出问题 |
| EVIDENCE | 展示事实或数据 |
| COMPARISON | 对比 |
| REVEAL | 揭示关键发现 |
| EXPLANATION | 解释原因或原理 |
| INSIGHT | 表达洞察 |
| CONCLUSION | 总结 |
| CTA | 互动引导 |

不同内容线可以使用不同的节点组合。

不要强迫四条生产线采用完全一样的脚本结构。

## 7.4 兼容性要求

目前已有脚本契约不能一次性推翻。

建议：

1. 保留当前 v1 输入和输出。
2. 增加版本化的 v2 契约。
3. 通过适配层兼容已有生产管线。
4. 逐条内容线升级。
5. 为不同版本增加契约测试。
6. 只有当真实生产验证稳定后，才考虑淘汰 v1。

## 7.5 关键修复要求

DATA_BOARD 的脚本作者必须真正接收并使用已经冻结的：

- editorialIntent
- storyAngle
- coreThesis
- audienceValue
- hookStrategy

这些内容不能只是保存在策划对象中，而没有传递给后续脚本生成步骤。

所有下游 Agent 和模型调用都必须基于同一份冻结的编辑方案。

# 8. 分镜系统（Storyboard）

**分镜是 Heron 从文案生成工具升级为内容生产系统的关键。**

脚本决定讲什么，分镜决定观众看到什么。

两者不能混为一谈。

## 8.1 每个场景需要规划

- 场景的叙事目的。
- 旁白。
- 画面主体。
- 视觉焦点。
- 需要展示的数据。
- 是否需要图片、视频或图表。
- 动效类型。
- 场景进入方式。
- 场景退出方式。
- 预计时长。
- 对应的 TTS 时间范围。

## 8.2 建议建设的视觉组件分类

### 数据组件

- 排名列表。
- 动态柱状图。
- 折线图。
- 面积图。
- 对比图。
- 雷达图。
- 数据卡片。
- 数字翻转。
- 时间轴。
- 数据地图（仅在数据契约和渲染能力完整后启用）。

### 叙事组件

- 大标题。
- 悬念揭示。
- 观点强调。
- 前后对比。
- 结论卡片。
- 引用来源卡片。
- 关键事实强调。
- 问题引导。

### 动效组件

- 镜头推进。
- 遮罩揭示。
- 分层进入。
- 数字递增。
- 图表排序。
- 节奏转场。
- 场景连续运动。

### 媒体组件

- 视频背景。
- 图片主体。
- 产品演示。
- 图标和品牌素材。
- 音效。
- 背景音乐。

所有视觉组件应当有清晰的输入契约，不允许模型随意组合出无法渲染的内容。

## 8.3 模板与风格

保持模板、视觉风格和内容生产线独立。

一个模板可以被多条生产线使用。

建议先发展以下视觉风格：

1. Professional News：专业新闻播报。
2. Data Investigation：数据调查。
3. Dynamic Data Explainer：动态数据解释。
4. Editorial Documentary：纪录片式表达。
5. Minimal Knowledge：极简知识讲解。
6. Cinematic Explainer：电影感解释。

风格是视觉表达策略，不是新增内容生产线。

一个栏目可以选择多个模板，同一个模板也可以服务多个栏目。

# 9. 事实、数据和素材管理

## 9.1 证据必须可追溯

所有重要事实都应该关联 Evidence ID。

不应该只保存模型生成的最终文字。

每条证据至少有：

- 来源名称。
- 来源地址或内部数据源标识。
- 采集时间。
- 发布时间。
- 原始内容或数据。
- 统计时间范围。
- 单位和口径。
- 核验状态。
- 适用范围。
- 对应的事实引用标识。

## 9.2 数据快照必须不可静默变化

DATA_BOARD 生产尤其需要保证：

- 选题使用的数据版本。
- 脚本引用的数据版本。
- 图表使用的数据版本。
- 最终视频显示的数据版本。

必须保持一致。

建议保存数据快照的版本标识、哈希和来源记录。

如果采集后的数据发生变化，需要明确标记重新核验，不允许脚本使用旧事实而图表使用新事实。

## 9.3 外部素材

素材可以来自：

- 授权视频和图片库。
- 用户提供的素材。
- 自有素材。
- 经过授权的生成式图片和视频。
- 具有明确许可的公共素材。

可将 yt-dlp 作为参考视频采集和分析工具，但不能将下载能力直接等同于素材使用权。

每份素材应保留来源、许可、使用范围和归属信息。

# 10. 音频与 TTS 体系

所有生产线共用统一音频生产能力。

但允许根据内容线配置不同的声音策略。

| 内容线 | 语音要求 |
|---|---|
| 热点新闻 | 专业、清晰、信息传递准确 |
| 数据看板 | 节奏明确、数字清楚、重点突出 |
| 趋势洞察 | 自然、稳重、有分析感 |
| 知识解释 | 亲和、易懂、语气有变化 |

## 10.1 核心要求

- 旁白与最终视频时间轴一致。
- 重要数字读法正确。
- 避免不自然的停顿。
- 避免多段 TTS 音色漂移。
- 背景音乐不能遮盖旁白。
- 需要支持片头、主体和结尾不同音量策略。
- 生成失败可以单独重试。
- 保存 TTS 供应商、模型和参数。

## 10.2 后续优化

可测试 VoiceStudio 或其他语音引擎，但任何新语音供应商都必须经过真实普通话样本测试。

不能因为模型支持的语言数量更多，就认为中文播报质量更好。

---

# 11. 质量审核体系

质量审核不能只检查视频是否能够成功渲染。

Heron 必须区分：

- 技术质量。
- 事实质量。
- 叙事质量。
- 视觉质量。
- 音频质量。
- 发布安全。

## 11.1 技术质量门禁

包括：

- 视频分辨率。
- 帧率。
- 视频时长。
- 音频是否存在。
- 音画时间是否正确。
- 黑屏检测。
- 冻结帧检测。
- 编码和容器合法性。
- 字幕是否越界。
- 渲染是否成功。
- 最终文件是否完整。

FFmpeg 和 FFprobe 负责可自动验证的部分。

## 11.2 事实质量门禁

包括：

- 关键事实是否有来源。
- 数据是否与快照一致。
- 时间和单位是否正确。
- 是否存在相互矛盾的信息。
- 是否出现无证据的因果判断。
- 是否出现夸大表达。
- 是否把推测描述成确定事实。

## 11.3 叙事质量门禁

审核：

- 前几秒是否有明确吸引点。
- 观众是否容易理解主题。
- 叙事是否连贯。
- 每个场景是否有必要。
- 是否有重复信息。
- 中间是否存在明显的节奏断层。
- 结尾是否真正传递了价值。

## 11.4 视觉质量门禁

审核：

- 文字可读性。
- 图表准确性。
- 图表动画是否帮助理解。
- 画面是否单调。
- 是否存在长时间静止画面。
- 场景是否重复。
- 画面是否与旁白一致。
- 动效是否过多或过少。
- 视觉风格是否统一。

建议除了 contact sheet 外，增加关键时间点截图审核。

技术检查与主观视觉判断必须分别记录。

## 11.5 音频质量门禁

审核：

- 旁白清晰度。
- 背景音乐音量。
- 音频削波。
- 突然静音。
- 语音停顿。
- 旁白与字幕匹配。
- 结尾淡出是否自然。

## 11.6 不同生产线的审核重点

| 质量项目 | 新闻 | 数据看板 | 趋势洞察 | 知识解释 |
|---|---|---|---|---|
| 时效性 | 高 | 中 | 中 | 低 |
| 数据准确性 | 高 | 极高 | 极高 | 中 |
| 来源核验 | 极高 | 极高 | 极高 | 高 |
| 逻辑完整性 | 高 | 高 | 极高 | 极高 |
| 视觉可读性 | 高 | 极高 | 高 | 高 |
| 解释清晰度 | 高 | 高 | 极高 | 极高 |
| 时长和节奏 | 高 | 高 | 高 | 高 |

质量门禁应能输出具体问题、严重程度、证据和修复建议，而不只是返回一个总分。

---

# 12. 发布体系

所有生产线共用发布系统。

统一管理：

- 视频文件。
- 标题和描述。
- 封面。
- 标签。
- 发布渠道。
- 发布时间。
- 发布尝试记录。
- 发布状态。
- 外部平台作品 ID。
- 发布结果核对。

必须延续当前发布安全设计：

- 发布前持久化发布尝试。
- 响应不明确时保留 UNKNOWN 状态。
- UNKNOWN 时不能直接重复上传。
- 人工核对后才能进行相应的重新提交。
- 自动发布必须经过明确授权和配置。

发布能力与内容线解耦，不允许每条内容线单独维护一套发布逻辑。

---

# 13. 数据反馈与内容优化

这是决定 Heron 能否越来越懂观众的重要部分。

目前不能只靠 AI 自己评判视频是否优秀。

必须逐步建立真实发布表现的数据体系。

## 13.1 收集指标

建议采集：

| 指标 | 作用 |
|---|---|
| 曝光量 | 内容获得多少展示 |
| 播放量 | 内容实际播放情况 |
| 3 秒留存 | 开场吸引力 |
| 平均播放时长 | 整体吸引力 |
| 完播率 | 内容完成度 |
| 点赞率 | 内容认可度 |
| 评论率 | 讨论价值 |
| 分享率 | 传播价值 |
| 收藏率 | 长期价值 |
| 关注转化率 | 账号吸引力 |

不同平台可能存在统计定义差异，必须保留平台和指标口径。

## 13.2 分析维度

必须支持：

- 按内容生产线分析。
- 按栏目分析。
- 按选题类型分析。
- 按标题策略分析。
- 按开场钩子分析。
- 按故事结构分析。
- 按视频风格分析。
- 按时长区间分析。
- 按发布时间分析。

## 13.3 内容表现分析

例如：

某个视频播放量不错，但完播率低。

系统应该进一步分析：

- 开场是否吸引人？
- 中间是否信息重复？
- 是否存在过长的数据展示？
- 是否有语音和画面不匹配？
- 是否是视频时长不合适？

再把这些结果沉淀成下一次策划的参考。

## 13.4 防止错误优化

不能因为一条视频播放量高，就认定它的全部特征都有效。

需要考虑：

- 样本量。
- 发布时间。
- 平台推荐差异。
- 视频时长。
- 选题热度。
- 内容质量。
- 流量异常。

样本不足时必须标注结论不可靠。

表现分析应先提供建议和可解释依据，不应直接自动修改所有内容策略。

# 14. Agent 设计

不建议为了四条内容线创建四套完全独立的 Agent 体系。

建议采用统一编排、职责分离的角色设计。

| 角色 | 主要职责 |
|---|---|
| Topic Scout | 发现和整理候选选题 |
| Editorial Director | 选择内容线、栏目和故事角度 |
| Researcher | 收集数据与证据 |
| Fact Reviewer | 核验事实和引用 |
| Script Author | 生成符合契约的旁白与脚本 |
| Storyboard Planner | 设计场景、视觉重点和动效意图 |
| Content Reviewer | 审核叙事、视觉与整体内容质量 |
| Performance Analyst | 分析真实发布表现 |

角色可以由现有 AgentScope Java 2.0 能力实现，也可以复用当前服务中的模型调用。

以上是逻辑职责，不意味着每个角色都必须部署为独立服务或独立长驻 Agent。

## 14.1 不同内容线的策略注入

每次生产都必须明确携带：

```text
contentLine
series
editorialIntent
storyAngle
audience
coreThesis
evidencePack
storyPlan
visualStrategy
qualityPolicy
```

不同内容线通过策略配置和对应的提示词、契约来完成差异化生产。

不能通过在一个巨大 Prompt 中简单堆叠所有生产线的规则实现扩展。

## 15.7 数据模型设计原则

- 栏目必须归属于内容线。

- 事实证据必须可追溯。
- Story Plan 和 Storyboard 必须有版本。
- 视频产物必须记录模板、渲染配置和文件指纹。
- 性能数据必须保留采集时间和统计口径。
- 所有重要数据结构必须向后兼容。

# 16. 前端产品结构

Heron UI 应围绕完整内容生产生命周期组织，而不是只围绕技术模块组织菜单。

建议采用以下主要功能：

## 16.1 内容总览

展示：

- 今日发现的选题。
- 待策划内容。
- 正在生产的视频。
- 待审核的视频。
- 待发布的视频。
- 最近发布表现。
- 各内容线生产情况。

## 16.2 内容发现

集中展示各条生产线发现的候选内容。

支持：

- 按内容线筛选。
- 按栏目筛选。
- 按评分排序。
- 查看原始来源。
- 查看推荐理由。
- 手动选择生产线。
- 加入生产队列。
- 拒绝选题。

## 16.3 编辑工作台

展示：

- 选题。
- 内容线和栏目。
- 核心观点。
- 故事角度。
- 目标观众。
- 证据列表。
- 故事计划。
- 脚本。
- 分镜。

支持人工修改和确认。

## 16.4 视频制作工作台

展示：

- 分镜卡片。
- 每个场景的视觉表达。
- 素材预览。
- TTS 音频。
- 场景时间轴。
- 渲染预览。
- 技术质量检查。
- 内容质量检查。

应支持单个场景返工，避免修改一个场景就重新生成整个视频。

## 16.5 内容审核工作台

支持按内容、事实、视觉和音频审核。

审核结果必须能够定位到具体场景和具体问题。

## 16.6 效果分析

展示：

- 各生产线表现。
- 各栏目的表现。
- 不同选题类型表现。
- 标题和开场表现。
- 模板和视觉风格表现。
- 完播和互动表现。

不能只显示播放量排行榜。

# 17. 初期内容比例与运营策略

初期建议采用以下内容资源配比：

| 生产线 | 初期建议比例 | 定位 |
|---|---:|---|
| 数据看板线 | 60% | 核心持续产出 |
| 趋势洞察线 | 20% | 内容深度和差异化 |
| 热点新闻线 | 10% | 捕捉短期热点 |
| 知识解释线 | 10% | 长期内容资产 |

这是初始资源分配建议，不是强制发布数量。

系统必须允许：

- 某条生产线当天没有值得生产的内容。
- 某个栏目连续一段时间没有合适选题。
- 热点不足时不生产新闻。
- 数据质量不够时不生产数据视频。
- 高价值选题优先于固定发布计划。

之后按照真实表现调整生产资源。

不能为了满足配比而生产低质量视频。

# 18. 分阶段实施计划

## P0：巩固现有生产链

目标：让现有 DATA_BOARD 真正具备内容导演能力。

重点事项：

1. 打通 Editorial Brief 到 DatasetScriptAuthor 的完整上下文。
2. 保证 editorialIntent、storyAngle 真正影响脚本。
3. 解决选题快照与实际生产数据不一致的问题。
4. 增强 Story Plan 和场景视觉意图。
5. 校验 TTS 时间线和字幕时间。
6. 加强 BGM、旁白和最终音频质量。
7. 加强关键帧截图审核。
8. 建立统一内容质量报告。

验收标准：

- 编辑策划不是摆设，确实影响最终脚本。
- 画面和旁白表达的是同一件事。
- 视频数据可以追溯。
- 可以通过 NO_PUBLISH 阻止低质量内容。
- 可以单场景返工。

## P1：建立趋势洞察线

目标：复用现有数据能力，生产具有分析价值的视频。

重点事项：

1. 增加 TREND_INSIGHT 策略。
2. 增加跨时间数据分析。
3. 增加多来源证据整合。
4. 增加趋势证据审核。
5. 增加趋势类 Story Plan。
6. 增加趋势类视觉表达策略。
7. 建立趋势选题质量评价。

验收标准：

- 能生成至少 5 个有证据支撑的趋势选题。
- 能完成多时间点数据分析。
- 能区分趋势、短期波动和推测。
- 能生成一组可实际渲染的趋势视频。

## P2：建立知识解释线

目标：扩大 Heron 的内容主题覆盖范围。

重点事项：

1. 增加 KNOWLEDGE_EXPLAINER 策略。
2. 增加知识检索和来源管理。
3. 增加概念拆解。
4. 增加知识类 Story Beat。
5. 增加知识类分镜和视觉组件。
6. 增加解释清晰度评价。

验收标准：

- 可以将一个专业主题拆解成普通观众能够理解的短视频。
- 重要概念和结论可追溯。
- 视频表达不存在关键概念错误。
- 能够支持案例讲解和原理拆解。

## P3：完善效果反馈闭环

目标：让 Heron 根据真实观众反馈持续改善。

重点事项：

1. 完善发布数据收集。
2. 增加 3 秒留存和平均播放时长等指标。
3. 建立选题与发布表现关联。
4. 建立标题、开场和模板表现分析。
5. 建立低样本量保护。
6. 生成内容优化建议。
7. 验证改进策略是否真的带来效果。

验收标准：

- 能够比较不同生产线的真实效果。
- 能够发现低完播视频的问题类型。
- 能够生成有证据的优化建议。
- 能验证策略调整前后的差异。
- 不会因单条视频偶然爆发而盲目改变系统策略。

# 19. 项目验收标准

最终不能用“功能完成”“能够生成 MP4”作为唯一验收标准。

必须通过以下几个维度。

## 19.1 内容能力

- 四条生产线具有清晰的选题和策划策略。
- 四条生产线能够共享生产基础设施。
- 各条线拥有对应的故事结构。
- 选题、脚本和视觉表达保持一致。

## 19.2 视频表现

- 开场具有明确吸引点。
- 场景切换符合叙事节奏。
- 数据和图表表达准确。
- 字幕和旁白同步。
- 音乐不干扰旁白。
- 视觉风格统一但不过度模板化。
- 不存在明显的长时间无意义画面。

## 19.3 自动化能力

- 支持批量生产。
- 支持幂等和失败重试。
- 支持局部返工。
- 支持人工审核。
- 支持 NO_PUBLISH。
- 支持发布结果核对。

## 19.4 数据闭环

- 可以追踪每条视频的生产策略。
- 可以关联发布表现。
- 可以按内容线和栏目分析。
- 可以解释优化建议。
- 不会对小样本数据过度拟合。

## 19.5 生产测试

建议至少完成：

- 每条内容线 5 条真实内容样本。
- 真实 TTS 生成。
- 真实 HyperFrames 渲染。
- FFmpeg 最终后处理。
- 完整 QA。
- 人工视觉审核。
- 记录生产成本、耗时和失败原因。

样本只用于验证生产质量，不代表已经证明能够产生热门视频。

热门能力需要依靠长期发布数据验证。

# 20. 关键技术约束与实施纪律

1. 保留现有 Java / Spring Boot / JDK 21 技术体系。
2. 保留当前 AgentScope Java 2.0 集成方向。
3. 保留 HyperFrames + GSAP + FFmpeg 视频制作体系。
4. 保留 MinIO 媒体存储体系。
5. 不未经论证引入第二套渲染框架。
6. 不为每条生产线创建独立微服务。
7. 不因为增加 Agent 而引入过度复杂的 Agent 网络。
8. 生产链必须支持幂等、失败重试和任务恢复。
9. 内容方案、数据快照、证据和最终视频必须可追溯。
10. 不改变已有发布安全机制。
11. 数据库变更必须采用项目统一的 Flyway 迁移方式，并与部署流程保持一致。
12. 生产环境、数据库和部署文件必须保持安全，不进行未经授权的操作。
13. 不自动提交 Git、不推送代码、不发布真实视频，除非获得明确授权。
14. 所有新功能必须配套测试和文档。

# 21. 当前代码演进中的优先检查项

本架构是目标设计，不代表当前所有能力已经实现。

以本次已审查的 dev 分支代码为基础，进入新阶段之前应优先核查：

1. **DATA_BOARD 编辑上下文传递：** 确保 editorialIntent 和 storyAngle 真正进入脚本作者，不能只保存在上游策划数据里。
2. **数据快照一致性：** 确保选题冻结时的数据和实际渲染使用的数据一致。
3. **脚本与分镜结构：** 现有 lead/body 脚本契约需要逐步升级，不能只在提示词里要求更好的故事。
4. **视觉审核：** 现有技术检查需要补充关键帧审核和场景级质量判断。
5. **效果数据：** 当前以人工指标录入为主，应逐步建立可追溯的表现数据采集机制。
6. **数据库迁移：** 新增发布尝试相关表需要与实际 Flyway 迁移流程统一，不能只依赖手工 SQL。
7. **代码仓库安全：** 检查提交到公共仓库的大体积日志文件和部署配置中的默认凭据，确认是否存在敏感信息。

以上项目都应先通过代码和测试验证，再进行功能扩展。

# 22. 最终架构结论

Heron 的长期发展方向不是拥有越来越多的视频模板，也不是把越来越多的 AI 工具拼在一起。

而是建立一套真正具备内容生产能力的体系：

- 热点新闻线：发现事件。
- 数据看板线：展示事实。
- 趋势洞察线：发现变化。
- 知识解释线：讲清原理。

四条生产线拥有不同的内容策略，却共享相同的生产基础设施。

整个系统围绕编辑策划、事实证据、故事结构、场景分镜和真实观众反馈运行。

最终目标：

**让 Heron 不只是能够自动生成视频，而是能够判断什么值得讲、知道应该怎么讲、懂得怎样用画面讲，并通过真实观众的反馈，持续提高内容质量。**

这是 Heron 从 AI 视频自动化工具，走向智能内容生产平台的核心方向。
