# Heron AgentScope + JEV 最终架构设计：独立架构评审任务

你现在是一名资深 AI Agent 架构师、分布式系统架构师和企业级 Java 系统设计专家。

请对 Heron 项目最新的 AgentScope Java 2.0 + HarnessAgent + JEV 架构进行独立、深入的架构评审。

这不是简单的文档润色，而是一次正式的架构设计审查。

你的核心任务是判断：将 JEV 纳入 Heron 后，是否真正形成了一套可靠、可观测、可治理、可持续演进的 Agent 系统。

## 一、理解 Heron 的最终目标

Heron 是自动化短视频生产平台。

未来希望实现：

- 自动发现值得生产的内容机会。
- 自动分析账号、视频、行业和趋势数据。
- Agent 自主决定需要进一步查询的数据。
- 动态调整调查策略。
- 多 Agent 分工协作。
- 独立事实核验。
- 自动判断内容是否值得生产。
- 自动生成脚本和视频。
- 自动执行质量检查。
- 自动发布并回收效果。
- 根据历史发布效果持续优化决策策略。

数据看板内容线是主要生产来源，新闻线是辅助生产来源。

新闻不是采集到就发布，而是必须经过内容价值判断、事实核验和生产可行性评估。

人工主要负责监督、处理异常和策略调整，而不是每个环节都手动操作。

## 二、必须理解的核心技术定位

Heron 采用三类核心技术能力：

### AgentScope Java 2.0

负责 Agent 的运行和执行：

- HarnessAgent。
- ReActAgent。
- Subagents。
- Skills。
- Workspace。
- Memory。
- Context Management。
- Session Log。
- Tool 调用。
- 自主规划。

HarnessAgent 作为复杂任务的主要执行器，ReActAgent 负责轻量任务。

### JEV

负责语义判断、评估、验证和治理：

- Judge API。
- Trace Evaluation。
- Tool Guard。
- Supervision。
- Tool Selection。
- Content Guardrail。
- Context Compaction。
- Answer Refinement。
- Model Routing。
- Phase / Team Routing。

### Heron 原有确定性业务层

负责真正的业务事实和业务执行：

- 数据采集。
- 数据计算。
- 数据快照。
- 业务状态。
- 任务持久化。
- 幂等和恢复。
- 租户权限。
- 生产任务。
- 视频生产。
- 质量门禁。
- 发布。
- 效果回流。

这三者不能互相替代。

## 三、重点评审一：整体架构是否合理

请从架构角度判断：

1. HarnessAgent 是否适合作为 Heron 的核心 Agent 执行框架？
2. ReActAgent 和 HarnessAgent 是否存在职责重叠？
3. 是否有必要引入 Subagents？
4. 多 Agent 是否应该由 Supervisor 动态调度？
5. JEV 是否应该作为独立治理层，还是以 Middleware、Evaluator、Guard 等方式分散嵌入？
6. JEV 与 HarnessAgent 的边界是否清晰？
7. 是否存在重复评估、重复调用模型、重复消耗 Token 的情况？
8. 是否会出现 Agent 互相评价、互相修订、无限循环的问题？
9. 是否存在 AgentScope Session 与 Heron 业务任务状态重复建设的问题？
10. 是否会导致系统过度复杂？

请明确指出应该保留、合并、延后或删除的设计。

## 四、重点评审二：JEV 是否真的有必要全部引入

不要因为 JEV 提供了很多能力，就认为所有能力都必须接入。

请逐项评估：

| JEV 能力 | 需要回答的问题 |
|---|---|
| Judge | 哪些业务决策必须经过 Judge？ |
| Trace Evaluation | 是否应该每次任务都评估完整轨迹？ |
| Tool Guard | 哪些工具必须保护？ |
| Supervision | 哪些任务需要持续监督？ |
| Tool Selection | 何时才有必要动态筛选工具？ |
| Content Guardrail | 是否与现有内容质量门禁重复？ |
| Context Compaction | 何种任务才需要压缩？ |
| Answer Refinement | 是否可能产生无限修订？ |
| Model Routing | 如何避免路由决策本身增加不必要成本？ |
| Phase / Team Routing | 是否应该由 Supervisor 统一控制？ |

给每项能力标记：

- P0：首期必须具备。
- P1：有明确需求后引入。
- P2：暂时不引入。
- 不建议：存在明显重复或投入产出不合理。

每项判断都必须说明理由。

## 六、重点评审四：安全性与可靠性

重点检查以下风险：

- Prompt Injection。
- 间接指令注入。
- Agent 越权调用工具。
- 跨租户数据泄露。
- 自由 SQL。
- 任意 Shell 执行。
- 任意文件系统访问。
- 重复创建生产任务。
- 重复发布视频。
- Agent 错误判断任务已完成。
- JEV 评估失败却被当成 PASS。
- JEV 超时导致主任务阻塞。
- 工具执行成功但结果未持久化。
- 上下文压缩丢失关键证据。
- 多副本部署时 Session 和 Workspace 不一致。
- 长任务执行过程中服务重启。
- Agent 任务恢复后重复执行外部操作。

必须特别区分：

- 语义判断。
- 业务授权。
- 业务验证。
- 操作执行。
- 操作成功证明。

JEV 不得替代 Heron 后端真正的权限控制、幂等和业务验证。

## 七、重点评审五：评估体系和成本控制

设计一个能够衡量 Agent 实际价值的评估体系。

至少考虑：

- 数据事实准确率。
- 工具选择准确率。
- 工具结果使用正确率。
- 事实核验通过率。
- 选题判断准确率。
- 选题新颖性。
- 内容吸引力。
- 内容制作可行性。
- 内容审核通过率。
- 视频生产成功率。
- 发布成功率。
- 最终视频表现。
- 单任务 Token 消耗。
- 单个有效选题成本。
- 单个有效发布视频成本。
- Agent 执行延迟。
- 人工介入比例。

请给出普通 LLM、ReActAgent、HarnessAgent、多 Agent + JEV 的对照实验方案。

不要把模型调用次数越多、Agent 数量越多、评估环节越多当作质量更高。

最终要衡量：

**每消耗 1 元模型费用，Heron 能产出多少个经过验证、值得发布且实际表现良好的视频选题。**

## 八、重点评审六：JEV 的上线方式

必须考虑 JEV 不同组件的运行模式和限制。

初期优先使用 OFF / SHADOW 等不影响主业务执行的方式收集数据。

但不能假设所有 JEV 组件都支持相同的运行模式。

特别注意：

- Trace Evaluation 是轨迹评估，不能撤销已经发生的工具调用。
- Supervision 的建议不能直接证明任务完成。
- Tool Guard 不能替代 Heron 的业务授权。
- Judge 的概率阈值必须使用 Heron 自有数据校准。
- ERROR、INCONCLUSIVE、超时和预算耗尽不能默认当成 PASS。

请设计从观察、校准、有限约束到生产治理的完整上线策略。

## 九、架构优化要求

请以实际工程落地为标准：

1. 优先复用 AgentScope 和 JEV 官方已有能力。
2. 不要自己重新实现官方已有的 Agent 循环、Judge 或 Evaluator。
3. 不要为了统一接口而创建大量抽象层。
4. 不要重复实现 Heron 已经具备的业务能力。
5. 不要将 Agent 的短期上下文当作业务数据存储。
6. 不要让 JEV 成为所有业务请求的强制额外成本。
7. 不要让多 Agent 变成固定流水线。
8. 不要让 Agent 直接拥有生产数据库和发布权限。
9. 不要因为引入 JEV 而升级无关技术栈。
10. 尽量保持现有 Heron 业务流程稳定。
