# 三级策略、重复选题检测与 DISAGREE 验证

**日期：** 2026-11-16
**补完：** Phase 4/5 的三个已知缺口

---

## 一、L1/L2/L3：分级是换执行器，不是换参数

plan.md §12 的定义很具体，三档是三种技术方案：

| 等级 | 执行器 | 预算倍数 | 查工具 | 核验 |
|---|---|---|---|---|
| L1 | 普通 LLM（`chatWithoutUsage`） | 1.0 | 否 | 否 |
| L2 | ReActAgent | 2.0 | 是 | 否 |
| L3 | HarnessAgent | 3.0 | 是 | 是 |

### 定档看机会评分，不看人

`ResearchGrade.of(score)`：< 55 → L1，55–70 → L2，≥ 70 → L3。没评分的按最低档。

**为什么按数据定档**：让人选，人一定全选最高档。plan 自己写的「初始机会筛选尽量由 Java 完成，
只有达到相应价值阈值的内容才升级」也是这个意思——成本不该随机会数线性增长。

两个阈值是**起点不是定论**，它们决定成本曲线，应该按实际账单调。

### L2 真的用 ReActAgent

一开始我把 L2 也接到了 Harness 上，那是错的：plan 的口径就是 L2=ReActAgent。
Harness 额外带的是计划模式、任务清单、子 Agent 那一整套，中档机会用不上，
带着它们反而多一层可能出问题的地方。新增 `ResearchAgentFactory.createReAct` 走裸 ReActAgent。

### L1 的能力边界写死在提示词里

L1 拿不到实时数据，只能基于目标文本作答。所以它的系统提示词明确写着
「只允许给 OBSERVE 或 REJECT——没有查过数据就不该说值得做」。

这是刻意的：**一个不查数据的档位如果判 PRODUCE，会把整条链路的价值判断搞垮。**

### 真跑对比

```
L1（评分 52.63）  1 轮   0 次工具      48 token   250 字
L2（评分 69.94）  7 轮  12 次工具  约 4.7 万 token  3020 字
```

**差三个数量级。** 这就是分级的全部意义：不值得的机会不该花 L2 的钱。

## 二、重复选题检测接进建单入口

原实现只留了 `findExistingDecision` 一个查询方法，没人调用。现在接在 `createFor` 里，
且**在这之前就返回**——建单是花钱的入口，等跑完再提示重复，token 已经烧掉了。

顺序是：同日去重键 → 跨天已有未处理/已采纳决策 → 都没有才建新任务。

### 验收时发现的一个真缺陷

第一版直接返回「决策挂的研究 id」。但**那个研究可能已经被清理**，于是接口返回一个不存在的任务，
前端拿到 `data: null`。实测时就是因为造了一条假决策指向不存在的研究，才发现这个问题。

现在会回读一次：研究确实存在才复用，否则按新任务处理。日志里也留了痕。

查重失败（比如库抖动）不挡建单：宁可多花一次钱，也不要让用户点不动。

## 三、DISAGREE 路径：主动喂假结论

这条路径在真实链路里很难自然出现——核验员多数时候同意。但它是整个核验机制存在的理由，
不能只有单测覆盖。所以**主动给核验员一条与数据方向相反的结论**：

> 实际数据：AUD/CNY 从 0.4712 单调跌到 0.4599，-2.39%
> 伪造结论：「暴涨 15.3%，从 0.4712 升到 0.5420，创 30 年历史新高，值得立刻做成视频」

核验员的判定：

```
verdict=DISAGREE
reason=原始数据与结论方向完全相反……结论中的 0.5420 在整个序列里不存在，
       该序列最高值就是起点 0.4712……「创 30 年历史新高」更无依据：
       该源 totalRows 只有 8……无法支撑任何长期历史高点的判断

conflicts（5 条）：
  变化方向相反：数据为 -2.39%，结论称 +15.3%
  0.5420 在序列中不存在，8 个点的最大值仅为 0.4712
  「30 年历史新高」不成立：数据源总共 8 个点，覆盖一周
  快照标识 deadbeef 无效，机会记录中 snapshot 为 missing
  compare_series 返回 unsupported，无法交叉验证
```

它不只看方向，还把「3020 在序列里不存在」「8 个点撑不起 30 年新高」「快照标识无效」逐条揪出来。

这个场景已固化为常驻测试 `VerifierDisagreeRealTest`（`render` 组，需真模型），
同时保留一条对照用例：与数据一致的结论应判 `AGREE`，避免核验员变成「永远反对」。

## 四、验证

| 项 | 结果 |
|---|---|
| 单测 | 369 项全绿（新增 9 项：分级 5、查重 3、核验真跑 1 组 2 用例） |
| L1 真跑 | `grade=L1`，1 轮 0 工具 48 token |
| L2/L3 定档 | 评分 69.94 → L2；≥70 的走 L3 并触发核验 |
| 同日去重 | 同机会再点返回同一研究 id |
| 跨天查重 | 造待处理决策 → 复用了那条真实研究并重新排队 |
| 悬空 id 修复 | 决策指向已删除的研究 → 按新任务处理，不再返回 null |
| DISAGREE | 伪造结论被判 `DISAGREE` + 5 条具体冲突 |
| AGREE 对照 | 一致结论判 `AGREE` |

### 造的测试数据已清理

为验跨天查重临时插了两条 `decision_id` 以 `999000000000000x` 开头的假决策，验完已删。

## 五、还剩什么

- **每日预算**：plan §12.1 还列了「每日模型费用上限」「每日最大研究任务数量」，
  现在只有单任务闸，没有日级闸。
- **L3 的核验触发没在真实链路里跑过**：现有机会评分最高 69.94，够不到 70 的 L3 阈值，
  所以「L3 → 核验」这段只走了构造出来的核验测试，没走完整链路。
  要么降低阈值、要么等有更高分的机会。
- **阈值未经数据校准**：55/70 是拍的，应该按真实账单调。
