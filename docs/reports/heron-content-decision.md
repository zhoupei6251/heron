**日期：** 2026-11-16

## 一、Phase 5：决策为什么要单独一张表

最容易走的捷径是「决策就从 `heron_research_task.report_json` 里读，不用建表」。

不行，原因是**研究的生命周期和决策的生命周期不一样**：同一机会同一天只有一个研究任务，
重跑覆盖同一行报告；而决策一旦产生就是历史事实——重跑不该改写「当时人看过什么、怎么定的」。

所以 `heron_content_decision` 存的是**决策那一刻的快照**：判断、理由、置信度、
依据的快照标识（`evidence_ref` = 报告的 `data_sha256`）、模型与提示词版本，一并冻结。

### 唯一约束是关键

```sql
UNIQUE KEY uk_decision_research_attempt (research_id, attempt_no)
```

- 同一次执行重复触发 → 只落一条（幂等）。
- 重跑是新的 `attempt_no` → 落新的一条，**旧决策不被覆盖**。

并发插入撞唯一键时回读已存在的那条，不把异常抛给调用方。

### 没判断就不落决策

报告里 `decision` 为空时返回 `null`，不插行。编一条 `OBSERVE` 等于替模型做判断——
那和「模型说不知道」是两回事。

### 人工否决必须写理由

采纳可以不写，否决不行。说不出为什么否决的否决：事后没法复盘，也没法拿去改提示词。
这是唯一一处「为了流程完整性而拒绝请求」的地方，值得。

## 二、Phase 4：为什么没有打开 `disableSubagents()`

框架提供了 `subagent()`，但打开它意味着把一项我们一直**逐项关掉**的能力重新打开。
用业务层串行编排能做到同样的事，而且更好：

| | 框架 subagent | 业务层编排（选用） |
|---|---|---|
| 独立上下文 | 需要额外配置 | 天然——另一次 `factory.create` |
| 预算/账本 | 混在父 Agent 里 | 各自独立，`attempt_no + 1000` 区分 |
| 失败隔离 | 子 Agent 崩了主链路要处理 | try/catch 一行 |
| 安全开关 | 要开 `disableSubagents` | 不动 |

`plan.md §4.4` 的硬要求是「核验 Agent **不应只读取其他 Agent 的总结**」。
另起一段会话、另一份提示词（`verifier.md`）、同一批只读工具，正好满足——而且比框架委派更硬：
核验员连研究员的推理过程都看不到。

### 只核验 PRODUCE

判错成「不值得做」代价小——只是少做一条；判错成「值得做」会一路走到生产。
所以核验预算只花在 `PRODUCE` 上。配置项 `heron.agent.verify-enabled` 默认开。

### 核验结果不覆盖研究结论

`verification_verdict` / `verification_reason` / `verification_conflicts` 是独立三列。
研究员判 `PRODUCE`、核验员判 `DISAGREE`，这两个事实都要留给看的人——
合成一个字段就再也看不出冲突了。这正是 plan §4 验收要的「能识别不同 Agent 结论冲突」。

### `UNCERTAIN` 不是冲突

`DISAGREE` 才是「结论错了」。`UNCERTAIN` 说的是「数据不够，判断不了」。
混为一谈会让下游误以为发现了问题。代码里 `conflicted()` 只认 `DISAGREE`。

## 三、工具注册的一个坑

框架的 `Toolkit.registerTool` 用 `getDeclaredMethods()`——**只扫类自身声明的方法，不扫父类**。

所以核验的收尾工具 `submit_verification` 单独放在 `ResearchVerificationTool` 类里：
研究员注册「查询工具 + `submit_findings`」，核验员注册「查询工具 + `submit_verification`」，
两边的收尾动作不会串到对面。

## 四、验证

### 测试（新增 10 项，总 360 项全绿）

| 用例 | 断言 |
|---|---|
| 报告落决策 | decision / confidence / reason / 快照标识 / 模型 / 提示词版本全部冻结 |
| 无判断不落库 | `insert` 一次都不发生 |
| 同 attempt 幂等 | 返回已存在的 id |
| 并发撞唯一键 | 回读已存在那条，不抛异常 |
| 否决必填理由 | 空/null/空白都抛 400，且不写库 |
| 采纳可不填 | 正常落 accepted |
| 核验判定归一化 | `disagree` → `DISAGREE`；冲突项去重去空白 |
| **UNCERTAIN 不算冲突** | `conflicted()` 为 false |
| 核验参数校验 | 非法 verdict、空 reason 都拒绝 |
| 未交判定 | `submitted=false`，不伪装 |

## 五、真跑验收（2026-11-16）

重启后端（8085）与前端 dev（5176），从头走了一遍。

### 研究 → 决策 → 核验

```
研究 R2122178944873660416  partial  7 轮 12 次工具  decision=PRODUCE
决策 2122179197421092864   proposed  62%  快照 736e4bffe5…
核验 verdict=AGREE       核验账本 15 行（attempt_no 1000+ 与研究员分开）
```

**核验判了 AGREE，却列了 5 条具体问题**——这正是独立核验的价值所在：

- `-3.28%` 的基期是 11-04 的 4.6807，不是结论写的 11-03 的 4.6598；按结论给的端点算只有 -2.85%
- 「7 期」实际跨 9 个自然日（含周末缺口），是 7 个交易日观测点
- 7 个货币对的独立性被高估：DKK 钉住 EUR，两者数值近乎重合；且全部来自 frankfurter 同一上游
- 「人民币同步走强」缺了最关键的 USD/CNY

结论站得住但细节有瑕疵——`AGREE` 与 `conflicts` 非空可以并存，这两件事说的是不同的东西。

### 人工否决

- 空理由点确定 → 前端拦住（`否决必须写理由`），弹窗不关。
- 填理由后 → 状态变 `已否决`，`decided_by` 记真实用户 `1761100000000000001`，理由入库。

### 页面

决策列表显示判断/处理/核验/把握/机会/理由/快照/操作八列；详情弹窗把核验判定、理由
与冲突清单完整展开。浏览器里逐项确认过。

验收中顺手修了两处：核验结果一开始压根没渲染（后端加了字段、前端没画）；列数加到 9 列后
横向塞不下，操作列压住核验列——去掉列表里的时间列（详情里有），收窄其余列。

## 六、没验证的

- **`DISAGREE` 分支没有真实触发过**：这次核验判的是 `AGREE`，所以「核验员与研究员结论冲突」
  这条路径只有单测覆盖。
- **`findExistingDecision` 没接进触发链路**：Phase 5 写的「重复选题检测」只留了查询方法，
  没在研究入口处用它拦截或告警。
- **L1/L2/L3 三级策略没做**：现在所有研究都是同一套参数。
