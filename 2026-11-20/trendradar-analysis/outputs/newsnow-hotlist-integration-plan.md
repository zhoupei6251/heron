# NewsNow 热榜平台可用性与 heron 接入方案

- 日期：2026-11-20
- 关联文档：[TrendRadar 接入分析](./trendradar-analysis.md)
- 本轮范围：**只出方案，不写业务代码**
- 信息口径：平台可用性为 2026-11-20 当天实测（`newsnow.busiyi.world`）；heron 触点为当前仓库代码

---

## 一、结论摘要

**能用，但要走 NewsNow，不走 TrendRadar；接入方式是在现有来源模型里加一个 `newsnow` 类型，不是新建一套热榜系统。**

三个关键判断：

1. **平台确实可用**：抽样 11 个平台全部 HTTP 200，单次 0.9–1.1 秒，返回 10–30 条，数据新鲜度 0–29 分钟（与 NewsNow 约 30 分钟缓存一致）。
2. **它不是实时接口**：最坏情况约 30 分钟延迟；做「突发热点」可以，做「秒级榜单」不行。
3. **接进来会落进解说线候选，不是「纯热榜」**：现有 `hasBody` 的判定是「证据里有 sourceUrl」，NewsNow 条目带链接，会和现在的微博/百度一样进入 `articles` 候选；真正写稿时再按链接抓正文。知乎/抖音/头条等原站大概率反爬，正文抓取失败率会上升——这是方案里必须处理的一环，不是接入后才发现的意外。

## 二、抽样实测（2026-11-20）

### 2.1 结果

| 平台 ID | HTTP | 上游 status | 条数 | 数据年龄 | 耗时 | 首条字段 | 名次在 URL |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `weibo` | 200 | success | 30 | 0 min | 1145 ms | id/title/url/mobileUrl/extra | 是（`band_rank=1`） |
| `zhihu` | 200 | success | 20 | 0 min | 950 ms | id/title/url/extra | 否 |
| `douyin` | 200 | cache | 30 | 29 min | 962 ms | id/title/url | 否 |
| `bilibili-hot-search` | 200 | cache | 30 | 29 min | 927 ms | id/title/url/extra | 否 |
| `toutiao` | 200 | cache | 30 | 29 min | 866 ms | id/title/url/extra | 否 |
| `baidu` | 200 | cache | 30 | 26 min | 931 ms | id/title/url/extra | 否 |
| `thepaper` | 200 | success | 20 | 0 min | 925 ms | id/title/url/mobileUrl | 否 |
| `cls-hot` | 200 | success | 13 | 0 min | 902 ms | id/title/url | 否 |
| `wallstreetcn-hot` | 200 | success | 10 | 0 min | 893 ms | id/title/url | 否 |
| `tieba` | 200 | success | 30 | 0 min | 907 ms | id/title/url | 否 |
| `ifeng` | 200 | cache | 12 | 26 min | 904 ms | id/title/url/extra | 否 |

说明：

- `status=success` 表示本次触发了上游抓取（因此年龄 0 分钟）；`status=cache` 表示命中缓存，年龄最多约 30 分钟。
- 连续三次请求 `douyin`，`updatedTime` 不变，确认是缓存而非每次实时抓取。
- 响应头：`server=cloudflare`、`cf-cache-status=DYNAMIC`、无 `cache-control`、无 CORS 头；服务端不做浏览器跨域，只适合服务端调用。
- **非法平台 ID 返回 HTTP 500**（不是 4xx），适配器必须显式处理，不能当普通空结果。

### 2.2 返回结构

固定外壳：

```json
{
  "status": "success|cache",
  "id": "zhihu",
  "updatedTime": 1794534794956,
  "items": [
    { "id": "标题或平台条目 ID", "title": "标题", "url": "原文链接", "mobileUrl": "可选", "extra": {} }
  ]
}
```

差异点（决定映射方式）：

- **没有统一 rank 字段**：除微博把 `band_rank` 塞进 URL 外，其余平台的名次只能按数组顺序推导。
- **没有统一摘要**：知乎 `extra.info` 可能有补充信息；多数平台为空。
- **没有发布时间、作者、正文**：只有标题与链接。
- `id` 与 `title` 经常相同（微博、知乎），不能当稳定全局 ID 单独使用。

### 2.3 覆盖范围

NewsNow 服务端 `server/sources` 目前有 **46 个源文件**，一个文件可导出多个平台 ID，因此实际平台数是「数十个」，与官方说法一致。除上面 11 个外，还包括 36 氪、财新、观察者、懂球帝、豆瓣、虎扑、IT之家、掘金、快手、什么值得买、少数派、V2EX、雪球、联合早报等。

**但这不等于「46 个都能稳定用」**：每个源都是对目标站的抓取实现，目标站改版/风控都会让单个源失效。接入应按平台逐个灰度，而不是一次全开。

## 三、法务与合规边界

先把三样东西分开：**代码许可证、数据权利、抓取行为**。三者互不覆盖。

### 3.1 许可证

| 对象 | 许可 | 限制到哪一步 |
| --- | --- | --- |
| NewsNow | MIT | 可商用、可改、可分发；保留版权与许可声明即可。**只覆盖代码，不覆盖它抓到的数据** |
| TrendRadar | GPL-3.0 | 分发衍生作品时必须以 GPL 开放源码。内部自用一般不触发；一旦把代码并进 heron 并对外交付，就要按 GPL 处理整个衍生作品 |
| heron | 自有 | 不受上述许可证约束，但**不能把 GPL 代码拷进 `ruoyi-heron`** |

结论：

- 走 NewsNow（MIT）没有 copyleft 问题。
- 若坚持用 TrendRadar，只能独立容器 + 网络调用，且对外交付时要能提供其源码；不要复制它的解析器/配置进 heron。

### 3.2 数据权利

- 热榜标题通常较短、独创性有限，但**榜单的选取与编排**可能构成受保护的汇编/竞争利益；批量抓取转出再使用，存在反不正当竞争风险。
- 正文著作权归原站/作者；只取标题+链接、正文回原站抓取并遵守其条款，风险最低。
- 中国大陆还需注意《互联网新闻信息服务管理规定》：向公众提供新闻信息服务需要资质。heron 作为**内部选题工具**风险较低，但产出的视频对外发布时，应定位为「选题线索 + 原创解说」，不做新闻转载。

### 3.3 抓取行为

- 目标站的 robots、用户协议、频率限制仍然适用；**NewsNow 只是把抓取换了个地方发生，不转移责任**。
- 用托管版：请求打到 `newsnow.busiyi.world`，依赖第三方善意，无 SLA；抓取合法性由对方承担一部分，但数据来源风险仍在 heron。
- 自托管：抓取从自己的 IP 发出，合规责任完全回到自己身上，必须控制频率（建议 ≥600 秒/平台）。
- 建议上线口径（需法务确认）：**只存标题+链接+平台名，不存正文；正文按需回原站抓取；成片标注来源；不对外二次分发榜单数据**。

## 四、heron 现有模块的事实（接入前提）

| 事实 | 影响 |
| --- | --- |
| `NewsSourceBo` 的来源类型只允许 `rss\|atom\|text`，`weibo/baidu` 是迁移种子预置的 | 新增 `newsnow` 必须改后端校验 + 前端文案，否则页面存不进去 |
| `NewsSourceFetcher` 是 `switch(sourceType)`，新增类型只需加一个 case + 一个解析方法 | 这是最小改动路径的支点 |
| `NewsUrlPolicy` 只接受默认端口、拒绝 IP 字面量，出口还要过 `allowed-hosts` | **自托管在 `127.0.0.1:3000` 直接存不进去**；必须反代成域名+443，或改策略（需安全评审） |
| `canonical` 只剔除 `utm_*`/`fbclid`/`gclid` | 微博 NewsNow 链接带 `band_rank`，排名一变去重键就变，会产生重复候选；适配器必须自己剥掉 |
| `NewsCandidateCollector#upsert` 按规范链接/标题去重，累加 `hitCount`/`heatScore`，保留 `bestRank` | 排名取数组下标即可复用现有热度与名次逻辑，无需改表 |
| `EditorialLineEditor#hasBody` = 「证据里有 sourceUrl」 | NewsNow 条目带链接 → 进入 `articles`（解说线），不是 `hotHeadlines` |
| `FrozenArticleService` 写稿前按选中证据的 URL 抓正文，抓不到就失败 | 知乎/抖音/头条/微博原站反爬或登录墙会导致正文抓取失败；这是接入后要监控的主要失败面 |
| `NewsSourceRunner` 每 30 秒轮询、每批 2 个到期源，单源最小间隔 60 秒 | 现有调度够用；但 NewsNow 有 30 分钟缓存，间隔应设 ≥600 秒，别空转 |
| 无 MCP 客户端依赖 | 走 NewsNow 的 HTTP JSON，比走 TrendRadar MCP 简单得多 |

## 五、接入方案（三种，按改动从小到大）

### 方案 A：新增 `newsnow` 来源类型，复用现有来源模型（推荐）

**核心**：一个平台 = 一条 `heron_news_source`，`url` 存 `https://newsnow.busiyi.world/api/s?id=zhihu`，`sourceType=newsnow`。不建新表、不建新页面。

改动清单：

后端

1. `NewsSourceBo` 的类型正则加 `newsnow`。
2. `NewsSourceFetcher` 的 switch 加 `case "newsnow" -> parseNewsNow(body)`。
3. 新增 `parseNewsNow(byte[])`：
   - 解析 `items[]`；`title` → 标题，`url` → 链接，`id` → `sourceItemId`，下标+1 → `rank`；
   - `extra.info` 有值就作为 `summary`，否则留空；
   - 微博链接先剥掉 `band_rank`、`Refer`、`t` 再落地；
   - 非 JSON / 缺 `items` → `news_source_body`；HTTP 非 2xx → `news_source_status`（把上游 `id` 写进原因）。
4. 建议新增一个错误码 `news_source_empty`：`items` 为空视为失败并进告警，而不是静默成功。
5. `heron.news.allowed-hosts` 增加 `newsnow.busiyi.world`（托管）或自托管的内部域名。
6. 无数据库迁移；用页面或一条种子 SQL 预置 5 条来源即可。

前端（`heron-ui`）

7. 来源页 `sourceTypeText` 增加 `newsnow: 'NewsNow 热榜'`，表单提示「填写 NewsNow 接口地址」。
8. 来源类型下拉与查询筛选自动跟随，无需另做页面。

代价：

- 开发约 0.5–1 人日（含单测：用 5 个平台的离线 JSON fixture）；
- 运维：托管版零部署；自托管多一个 Node/Docker 服务；
- 风险：`allowed-hosts` 配错会全源失败；微博去重参数漏剥会产生重复候选；正文抓取失败率需观察。

**这是最小可行路径。**

### 方案 B：独立 NewsNow 平台目录 + 批量采集服务

**核心**：新建 `heron_news_platform` 表（平台码、名称、启用、间隔、上次结果），一个服务批量拉取，一个页面统一开关。

改动：

- 新表 + Flyway 迁移；
- 新的平台目录 Service/Controller/页面；
- 批量调度、共享限流、统一失败统计；
- 候选写入要么复用「合成来源行」，要么改造 `NewsCandidateCollector` 的入参。

代价：

- 开发约 3–5 人日；
- 与现有 `heron_news_source` 的启停/间隔/失败留痕重复，属于第二套模型；
- 只有在「要一次管 30+ 平台、且不想建 30 条来源」时才划算。

**结论**：当前不需要，属于过度设计。

### 方案 C：直连各站，自己写平台适配器

**核心**：在 `NewsSourceFetcher` 里为知乎/头条/B 站/抖音各写一个 parser，不经过 NewsNow。

代价：

- 每个平台 1–3 人日，且要持续跟进改版与签名；
- 抖音已经证明需要签名、返回空体，现有代码就是因此没接；
- 失败面成倍增加，且没有 NewsNow 的 30 分钟缓存与自适应抓取帮你挡频率。

**结论**：只在「必须拿到 NewsNow 没覆盖的站」时才考虑，且一次只做一个。

### 三种方案对比

| 维度 | A：`newsnow` 类型 | B：独立平台目录 | C：直连各站 |
| --- | --- | --- | --- |
| 改动面 | 小（1 个 case + 1 个解析器 + 校验/文案） | 大（新表+新服务+新页） | 中大（每站一个解析器） |
| 数据库 | 无 | 有迁移 | 无 |
| 平台扩展 | 加一条来源 | 加一行平台 | 写代码 |
| 失败可归因 | 源级错误码，天然复用 | 需另建一套 | 源级，但每站错误各不相同 |
| 运维 | 托管零部署 / 自托管 1 服务 | 1 服务 + 1 表 | 无额外服务，但反爬维护重 |
| 合规 | MIT，干净 | 同 A | 自己抓，责任最重 |
| 建议 | **首选** | 暂不需要 | 仅补缺口 |

## 六、最小可行排期（可据此排期）

| 步骤 | 内容 | 产出 | 预估 |
| --- | --- | --- | --- |
| 0 | 拍板：通道、首批平台、采集间隔、空结果语义 | 决策记录 | 0.5 天 |
| 1 | 后端：`newsnow` 类型 + 解析器 + 错误码 + 单测（离线 fixture） | 可编译、单测通过 | 0.5–1 天 |
| 2 | 前端：来源类型文案 + 新增/启停可用 | 页面可录入 | 0.5 天 |
| 3 | 配置：`allowed-hosts` + 预置 5 条来源（间隔 600s） | 可采集 | 0.5 天 |
| 4 | 灰度 3 天：观察每源失败数、空结果、候选增量、重复率、正文抓取失败率 | 灰度报告 | 3 天（观察） |
| 5 | 按数据扩平台或回滚（禁源即可，不改代码） | 结论 | 0.5 天 |

验收标准：

- 5 个平台在 30 分钟内各至少成功采集 1 次；
- 单源失败不影响其他源，错误码能回答「哪个源 + 什么输入 + 为什么」；
- 同一话题排名变化不产生重复候选；
- 关闭某源后不再产生新候选；
- 方案 A 不产生数据库结构变更。

## 七、需要你拍板的点（不替你做选择）

1. **数据通道**：NewsNow 托管直连 / 自托管 NewsNow / 各站直连 / TrendRadar 独立容器。
   - 影响：部署量、许可、稳定性、合规责任。
2. **自托管怎么落**：反代成域名 + 443（符合现有 SSRF 策略）还是放宽策略支持内网 `host:port`（需安全评审）。
   - 影响：是否要动 `NewsUrlPolicy`，动它就是动安全边界。
3. **首批平台**：建议候选 `weibo / zhihu / toutiao / bilibili-hot-search / baidu`；是否纳入 `douyin`（合规与风控更敏感）。
   - 影响：灰度范围与法务评估范围。
4. **采集间隔**：600s / 900s / 1800s。
   - 影响：新鲜度与对上游的压力；不建议低于 600s。
5. **空结果语义**：算成功（0 候选）还是失败（告警）。
   - 影响：告警噪声与「源失效」被发现的速度。
6. **NewsNow 链接是否允许进入正文抓取**：
   - 允许：解说线可继续用，但知乎/抖音等正文失败率会上升；
   - 不允许：需要改 `hasBody` 语义或把 NewsNow 条目标记为「纯选题线索」，这是行为变更，影响现有微博/百度。
7. **开放程度**：只预置 N 条来源供运营启停，还是允许运营在页面自助填任意 NewsNow 地址。
   - 影响：灵活性与安全边界。
8. **合规门槛**：是否先让法务确认「只存标题+链接、正文回原站、标注来源」的口径再上线；抖音是否单独评估。

## 八、风险与未验证项

**已确认的风险**

- 约 30 分钟数据延迟，不适合秒级热点。
- 平台名次只能按数组顺序推导，除微博外没有显式 rank。
- 微博 `band_rank` 会让去重键漂移，必须在适配器里剥掉。
- 非法平台返回 500，必须显式映射错误码。
- 知乎/抖音/头条/微博原站正文抓取大概率受限，会推高解说线的正文失败率。
- 托管版无 SLA、无 CORS、依赖第三方善意；生产建议自托管。

**未验证（不影响方案成立，属于灰度期验证项）**

- 46 个源逐个的长期可用率与失效周期；
- 各平台返回条目的排序是否严格等于站点热榜名次；
- 自托管 NewsNow 在当前网络环境下的部署成本与稳定性；
- 目标站对自托管 IP 的风控强度。

---

## 九、一句话答复

**这几十个热榜平台能用，但建议只把它当「标题线索源」，通过现有来源模型加一个 `newsnow` 类型接进来，先接 5 个、间隔 600 秒、灰度 3 天；不要为它新建一套热榜系统，也不要把 TrendRadar 的 GPL 代码并进 heron。**
